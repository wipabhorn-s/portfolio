Learnora

An online course marketplace where instructors sell video courses, learners buy and study them in the browser, and admins run the platform.

Why I built it

I wanted one project that I planned and built from start to finish on my own, covering everything a real product needs: requirements, a database, an API, a web app, sign-in, payments, file uploads and an admin area. An online course marketplace needs all of them at once, with real money and real files moving through it, so every shortcut shows.

Who it is for

Learners search for practical courses, pay with the methods people use in Thailand (cards, PromptPay, TrueMoney and mobile banking) and study at their own pace, picking up each lesson where they left off. Instructors publish video courses, set the price and how long access lasts, and receive 70% of each sale. Admins keep the marketplace fair: they moderate courses, decide refund requests and record instructor payouts. Teaching is a capability rather than a separate role, so one account can learn and teach.

Requirements first

Before writing code I wrote a Software Requirements Specification: five kinds of user (guest, student, instructor, admin and super admin), 71 functional requirements in 14 groups, and a 16-table data model. It became the checklist I built and tested against.

What it does

  • Checkout through Opn Payments with cards (including 3-D Secure), PromptPay QR, TrueMoney and mobile banking from five Thai banks. It runs in test mode, so no real money moves. Free courses are enrolled in one click.
  • Refund requests per course within 14 days, reviewed by an admin, who refunds only that course's price; the student is emailed either way.
  • Instructors create courses and upload videos of up to 100 MB straight from the browser to Cloudinary with a progress bar. Lessons play through signed links that expire after 6 hours, so shared links stop working.
  • Instructor earnings: a 70% share that becomes available once the refund window closes, a payout bank account stored encrypted, and payouts that admins record and the instructor is emailed about.
  • A complete account system: email verification, Google sign-in, two-factor authentication with an email code, sign out of every device, a lock after too many wrong passwords, and account deletion.
  • Course search with filters, sorting and pagination, instructor profiles, a wishlist, a cart, and a player that tracks progress per lesson.
  • An admin console with a revenue chart, user management, course moderation, payments, a refund queue and payouts. Super admins manage the admin accounts.

Challenges and decisions

100 MB videos on a host that accepts 4.5 MB requests

Vercel rejects large request bodies, so videos never pass through my server. The API signs a one-file upload ticket, the browser sends the file straight to Cloudinary, and when the lesson is saved the API asks Cloudinary itself whether the file exists, belongs to that instructor, is within the size limit, is a playable video and is not already used by another lesson.

Payments that are confirmed later

PromptPay, bank apps and 3-D Secure finish outside the site, and an old QR code can still be paid after a newer checkout. Each payment is settled from three places (the pending page, the Opn webhook and a background job), each one asks Opn for the real status, and every step is safe to repeat, so a course is never unlocked or refunded twice.

Refreshing login tokens with Server Components

Next.js Server Components cannot write cookies, so expired access tokens could not be refreshed while a page rendered. I moved the refresh into the proxy that runs before the page, rotated refresh tokens with reuse detection, and added a session version so every session can be ended at once.

A free server that falls asleep

The free API host sleeps after 15 minutes without traffic, which made the first login fail. A free pinger now keeps it awake, and if it is asleep anyway the web app waits and retries for up to 60 seconds instead of showing an error, without ever resending a payment.

What I learned

Most of the work in a real product is outside the happy path: a payment that is only confirmed later, a session that has to be ended on every device, a free server that is asleep when the first user arrives. Writing the requirements first made those cases visible early, and I learned to check the limits of each platform, like request sizes and cookies in Server Components, before building on top of it.
