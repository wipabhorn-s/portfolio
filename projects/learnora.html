Learnora

An online course marketplace where instructors sell video courses and learners buy and study them in the browser.

Why I built it

I wanted one project that I built from start to finish on my own and that covers everything a real product needs: a database, an API, a web app, sign-in, payments, file uploads and an admin area. An online course marketplace needs all of them at once, with real money and real files moving through it, so every shortcut shows.

Who it is for

Two groups use it. Instructors get a place to publish video courses, set their own price and receive 70% of each sale. Learners get practical courses they can pay for with the methods people use in Thailand, such as cards, PromptPay and TrueMoney, and study at their own pace, picking up where they left off. Admins keep the marketplace fair by reviewing courses, handling refunds and recording payouts.

What it does

  • Checkout through Opn Payments with cards (including 3-D Secure), PromptPay QR, TrueMoney and mobile banking, confirmed by webhooks. It runs in test mode, so no real money moves.
  • Instructors create courses and upload videos straight from the browser to Cloudinary with a progress bar; lessons play through signed links that expire.
  • A complete account system: sign-up with email verification, Google sign-in, 2FA, sign out of every device, and a lock after too many wrong passwords.
  • An admin area for users and courses, per-course refund approval, and records of the 70% instructor payouts.
  • Course search and filters, a wishlist, a cart and learning progress.

Challenges and decisions

100 MB videos on a host that accepts 4.5 MB requests

Vercel rejects large request bodies, so videos never pass through my server. The API signs an upload permission, the browser sends the file straight to Cloudinary, and when the lesson is saved the API asks Cloudinary itself whether the file exists, belongs to that instructor, is within the size limit and is not already used by another lesson.

Refreshing login tokens with Server Components

Next.js Server Components cannot write cookies, so expired access tokens could not be refreshed while a page rendered. I moved the refresh into the proxy (middleware) that runs before the page, rotated refresh tokens with reuse detection, and added a session version so every session can be revoked at once.

A free server that falls asleep

The free API host sleeps when idle, which made the first login fail. The web app now waits and retries the API for up to 60 seconds instead of showing an error.

What I learned

Most of the work in a real product is outside the happy path: a payment that is only confirmed later by a webhook, a session that has to be revoked on every device, a free server that is asleep when the first user arrives. I learned to design for those cases from the start, and to check the limits of each platform, like request sizes and cookies in Server Components, before building on top of it.
